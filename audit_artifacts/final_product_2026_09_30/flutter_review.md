## Findings

### F1 — P1 Critical — Reader page responses can arrive out of order, then confirm the wrong page

**Status:** Verified code defect; deterministic regression probe pending execution. **Affected flow:** rapid adult/kids Mushaf page turns, especially first corpus load; ordinary reading, daily wird, khatmah progress. **Trigger:** start loading page A, turn to page B, and let B finish before A. `QuranPageCubit.loadPage` emits every response without request ID/current-page check (`lib/features/quran/presentation/cubits/quran_page_cubit.dart:57-63`); both readers call it without awaiting/canceling prior loads (`lib/features/quran/presentation/pages/quran_reader_page.dart:331-335,763-772`; `lib/features/quran/presentation/pages/kids_quran_reader_page.dart:155-159`). The adult reader caches the returned detail and uses its page number/header (`quran_reader_page.dart:668-715`) although `_currentPageNumber` and the `PageController` already point at B. The rendered QCF page is managed by `AppQuranPageView`, so the proven issue is stale page metadata/highlights and stale Cubit state, not an assertion that Quran glyphs themselves are corrupt. More seriously, `confirmRead(pageNumber)` accepts any page while using `current.detail` without matching `detail.pageNumber` to the argument (`quran_page_cubit.dart:75-77,99-103,117-134`); the reader's gate invokes it for current B (`quran_reader_page.dart:343-357`). It can save B as read using A's details, suppress later retries via `isReadConfirmed`, and attach A's surah/ayah metadata to B's activity event. **User impact:** incorrect reading/progress evidence and wrong page context after a fast turn. **Reproduce:** controlled Futures for `getQuranPage(1/2)`, resolve 2 then 1; separately load 1 and call `confirmRead(2)`; the regression probes assert the required rejection/order. **Fix:** use a monotonically increasing request token or `restartable` semantics and ignore old completions; guard `confirmRead` so `current.detail.pageNumber == pageNumber`, and re-check state after every await before emitting or recording derived activity.

### F2 — P1 Critical — Stop or account reset during audio lookup can still start playback

**Status:** Verified code defect; deterministic regression probe pending execution. **Affected flow:** Quran recitation selection, kids reader audio, account sign-out/reset. `playSurah`, `playPage`, and single-ayah play set loading then await the Quran repository (`lib/core/services/quran_continuous_player_service.dart:219-259,262-300,307-355`). `stop()` clears the queue/state (`:530-538`) but does not invalidate the pending request. When the older lookup completes, it writes the queue and proceeds to `_loadPlaylistAndPlay`; that method also awaits background init, player stop, and source loading without an operation token (`:379-433`). The same applies to a later play request, allowing an earlier one to override the user's new selection. `AudioResumeStore.stopPlaybackForAccountReset` calls only `player.stop()` (`lib/core/services/audio_resume_store.dart:112-116`), so a lookup outstanding during sign-out can re-start the old account's recitation after reset. **User impact:** unwanted or wrong recitation, including after a user explicitly stopped it or switched accounts. **Reproduce:** delay `getSurahDetail`, call `playSurah`, call `stop`, then complete the lookup. The current implementation changes idle to error or proceeds to playback, depending on returned ayahs. **Fix:** operation generation/cancellation checked after every await before modifying queue/player/state; make stop and account reset invalidate pending operations and await or join final teardown.

### F3 — P2 Major — Cloud bookmark conflict can discard a newer local action when device clocks differ

**Status:** Strong code-supported risk; requires two-device/clock-skew runtime validation. **Affected flow:** bookmark creation/removal offline, then cloud reconciliation. Local revision uses device UTC milliseconds (`lib/features/quran/data/datasources/bookmark_service.dart:405-408`), and pull replaces an unsynced local bookmark whenever remote revision is greater (`:205-233`). The live `upsert_quran_bookmark` RPC uses `WHERE EXCLUDED.revision > quran_bookmarks_cloud.revision` (`audit_artifacts/final_product_2026_09_30/live_rpc_bodies.json`, `upsert_quran_bookmark` definition), so a different device whose clock is ahead can make a later offline local action lose to an older remote action. **User impact:** bookmark add/remove can silently revert after sign-in/resume. **Reproduce:** set device A clock ahead, sync bookmark revision R; on device B with earlier clock, toggle same bookmark offline and reconcile. **Fix:** server-assigned monotonic version or explicit conflict operation/timestamp policy that does not trust client wall clocks; preserve unresolved local mutations and surface conflict rather than replacing them.

### F4 — P2 Major — Notification plugin startup failure gates the whole application

**Status:** Strong code-supported risk; needs injected platform failure/device check. **Affected flow:** app launch when local notification initialization throws. `AppInitializer.initialize` awaits `_initNotifications` before marking initialization complete (`lib/core/services/app_initializer.dart:86-91,115-120`), while `_initNotifications` awaits the platform plugin (`:162-168`). The splash catches the error and offers only retry (`lib/features/splash/presentation/pages/splash_page.dart:44-77` and error UI), so a persistent notification plugin/platform failure prevents Quran reading and all offline content although notifications are auxiliary. **User impact:** whole app unusable on an affected device until plugin initialization succeeds. **Fix:** treat notification initialization as a recoverable degraded service; log/show notification-specific status and continue into the app, retrying settings/service initialization independently.

## Architecture and coverage notes

- **Quran reader and audio:** reader Cubits are GetIt factories and closed by their pages; global audio service and Cubit are lazy singletons (`lib/core/di/injection.dart:507-528,796-797`). Reader listeners, page controllers, timers and notifier disposal are present (`quran_reader_page.dart:212-229`; kids reader `:147-153`). The two concurrency defects above are the material mechanics gaps. QCF preloading runs for current plus eight nearby pages on each change (`quran_reader_page.dart:259-260,773-778`), but no measured frame/memory failure was established; do not promote that to a defect without a profile.
- **Startup:** lazy corpus preloading joins in-flight loads (`lib/features/quran/data/datasources/quran_local_datasource.dart:30-47,85-89`), reducing duplicate decode. Splash has a retry path for fatal initialization errors. Notification gating remains the specific recovery risk above.
- **Auth/account isolation and synchronization:** explicit account transition waits for current coordinator work before identity change (`lib/features/auth/presentation/cubits/auth_cubit.dart:367-385`; `lib/features/auth/application/cloud_sync_coordinator.dart:212-237`). Account reset stops playback and clears named preferences/Isar collections (`lib/core/identity/account_data_reset.dart:132-164`); bookmark storage and RPCs check active owner (`lib/features/quran/data/datasources/bookmark_service.dart:294-305,444-449`). Forced sign-out preserves pending bookmark recovery and barrier-blocks guest access (`auth_cubit.dart:500-550`). No independently verified cross-account data leak was found in those paths. Full sign-out, offline retry, remote merge and schema-policy behavior remain runtime unverified by this reviewer.
- **Cloud contract:** live `pull_quran_bookmarks` filters rows by `auth.uid()` and live `upsert_quran_bookmark` validates auth, verse bounds, payload size and increasing revision (`live_rpc_bodies.json`); these agree with the two BookmarkService calls (`bookmark_service.dart:205-216,241-275`). This confirms function shape, not live successful round trips or RLS behavior for every table. Other cloud RPC and policy comparisons are outside this narrow review and remain for the root's cloud audit.
- **Other product surfaces from inventory:** memorization session/review, kids progression, family linking, khatmah UI, azkar, prayer, notifications, progress, settings and sharing are covered by their specialist reviewers for user flows. I inspected shared DI, identity reset, cloud coordinator and reader integration to identify cross-feature mechanics. I did not claim complete runtime coverage of these surfaces.

**Readiness score for this assigned slice:** 68/100, based on two critical async races affecting reading/audio state and one cloud bookmark consistency risk. The score is an implementation review aid, not a product release verdict.
