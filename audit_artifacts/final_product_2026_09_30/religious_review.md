# Religious-content and Quran integrity review (read-only)

Snapshot: HEAD `1eefc8ae46639cf4026b6d7c7328ff4d36d3a0d6`, 2026-09-30. Scope: live Quran/Islamic content paths, not release configuration. This review used the current source and assets, the Quran safety contract (`.agents/skills/talia-quran-engineer-skill/references/quran-safety-contract.md`), the source policy (`docs/TALIA_ISLAMIC_CONTENT_SOURCES_POLICY.md`), and the repository inventory only as a route map. No application source was changed. No Android runtime or audio listening was available to this reviewer.

## Method and source boundary

- A read-only Node traversal parsed all `assets/data/quran.json` and `surahs.json` records; checked 114 surah IDs, 6,236 consecutive global and per-surah ayah IDs, surah count/first page/first juz, monotonic page and juz values, full 1–604/1–30 coverage, and all 126 `daily_ayahs.json` references. SHA-256 was recomputed for all four files in `content_manifest.json`. Results: no structural mismatch, all four hashes match, 126/126 daily references resolve. This is **internal consistency**, not proof of every word against an authoritative edition.
- External primary reference: [King Fahd Complex developer platform](https://qurancomplex.gov.sa/en/techquran/dev/) describes its Hafs `aya_text`, `aya_no`, `page`, and `jozz` fields and explicitly notes its corrected mapping for 27:56–59 to juz 20. A targeted comparison finds all four bundled records at page 382, juz 20 (`assets/data/quran.json`, surah `27`, verses `56`–`59`). The full official dataset was not obtained for a verse-by-verse comparison. The repository declares AlQuran Cloud `quran-uthmani` as the text source (`assets/data/content_manifest.json:31`) and a separate `qcf_quran_plus` rendering corpus (`:9`); their equality has not been established by the existing hash/version tests.
- External audio source: [EveryAyah's own ayah-recitation index](https://everyayah.com/recitations_ayat.html) lists the selected reciter families and verse-level MP3 service. This verifies the *service and naming scheme*, not each stream's identity, riwayah, file completeness, or verse boundary. The [King Fahd Complex audio page](https://qc-dev.qurancomplex.gov.sa/quran-audios/) is the policy's preferred licensed primary source, but these runtime URLs use EveryAyah.
- External adhkar source: [Dorar's original adhkar portal](https://dorar.net/azkar/wird) was inspected as a provenance comparator, and its [specific Abu al-Darda record](https://dorar.net/h/pqEtwkhl?osoul=1) confirms that a sevenfold “حسبي الله” wording exists. That narrow check **does not** authenticate the 116 release records or their individual counts, timings, translations and grades. No ungrounded Quran or hadith wording was generated or corrected.

## Findings

1. **P0 Release Blocker — credible religious provenance risk — Adhkar/dua and smart wird.** `assets/data/azkar_release.json:2`–`:5` contains 116 published `approved` records (30 Quran, 85 hadith, one dua), but only 31 carry `sourceUrl`; 66 of 85 hadith entries lack one, and all 85 have `authenticityGrade:null`. Examples `m5` cites only `صحيح مسلم`; `m6` cites `صحيح الترمذي`; `m12` cites `سنن أبي داود` with a seven-repeat prescription. None gives a specific hadith number, variant, grader and source link in the release record. `lib/features/azkar/data/models/zikr_model.dart:44`–`:48` accepts `approved` without checking that evidence; `:75`–`:92` accepts null grade; the normal screen shows reference without an authenticity grade (`lib/features/azkar/presentation/pages/azkar_category_page.dart:747`, `:761`). The user sees and may repeat a purported prophetic formula and count without a traceable individual source. The manifest's project-owner approval (`assets/data/content_manifest.json:5`–`:7`, `:62`–`:76`) is recorded, but it is not a record-by-record source comparison. **Status:** verified provenance gaps; *religious correctness remains unknown*, not a confirmed false hadith. **Remedy:** suspend unverifiable records or attach specific original hadith/adhkar links, edition/number, wording variant, count/time/virtue evidence and scholar decision per item; compare the rendered Arabic text and contextual claims before re-enabling. This is P0 until the content is verified under `docs/TALIA_ISLAMIC_CONTENT_SOURCES_POLICY.md:13`–`:20`.

2. **P0 Release Blocker — credible canonical cross-corpus risk — reader, bookmarks, highlights, memorization and audio alignment.** The page reader renders `qcf_quran_plus` data (`lib/features/quran/presentation/widgets/app_quran_page_view.dart:105`–`:108`, `:156`–`:166`), whereas metadata, search, saved text, listening questions and daily ayahs use bundled `quran.json` (`lib/features/quran/data/datasources/quran_local_datasource.dart:94`–`:151`; `lib/features/memorization_plus/data/listening/listening_quiz_source.dart:58`–`:79`). Bookmarks and long-press mapping ask QCF for the page (`lib/features/quran/domain/bookmark_reader_location.dart:7`; `lib/features/quran/presentation/pages/quran_reader_page.dart:508`) while the page-detail repository uses the JSON page field (`lib/features/quran/data/repositories/quran_repository_impl.dart:66`–`:80`). `test/assets/corpus_integrity_test.dart:228`–`:254` verifies only the QCF package lock digest, not per-ayah text/page equivalence. If these independently versioned corpora disagree, the selected/played/saved verse can refer to another page or wording. **Status:** credible risk and unknown; no actual verse/page mismatch demonstrated. **Remedy:** before release, deterministically compare all 6,236 `(surah, ayah, page)` mappings and normalized versus exact display text with a pinned, authoritative Hafs/Madinah source and the QCF rendering corpus; inspect a sample of pages and all affected UI, then reconcile with a reviewed migration plan for saved identifiers.

3. **P0 Release Blocker — confirmed non-verse code point in canonical text — al-Fatihah 1:1.** `assets/data/quran.json:1`, object `"1"[0].text`, begins with U+FEFF before `بِسْمِ`. A scan of all 6,236 texts found this one occurrence. `QuranLocalDatasourceImpl.parseQuranData` preserves the raw string (`lib/features/quran/data/datasources/quran_local_datasource.dart:132`–`:150`); daily ayah, sharing, memorization fallback, search or copy can inherit it. The onboarding widget explicitly strips a leading BOM (`lib/features/onboarding/presentation/widgets/onboarding_source_ayah.dart:46`–`:52`), showing that only one path compensates. **Status:** confirmed hidden format character, not a demonstrated wrong visible Arabic word; official exact text comparison pending. **Remedy:** obtain the approved source record for 1:1, deterministically remove or account for the extraneous code point in the source through the Quran safety approval path, update the manifest hash, and regression-check every consumer. Do not silently mutate the canon.

4. **P1 Critical — confirmed functionality failure — morning/evening/dua reminders.** Every one of the 116 `azkar_release.json:2`–`:5` records has `tier:null`; all hadith records also have a null `authenticityGrade`. `extractApprovedAzkarTexts` rejects a null tier (`lib/core/content/approved_azkar_content.dart:68`) and a non-Quran null grade (`:71`–`:74`), so the actual release corpus yields an empty list for every category. Reminder scheduling cancels the previous alarm first, then returns on the empty list (`lib/core/services/notification_service.dart:1468`–`:1472`, `:1512`–`:1516`, `:1558`–`:1563`). A real user enabling these reminders receives none, with no stated failure. **Status:** deterministic confirmed defect from all-record enumeration plus direct code path; device notification delivery was not exercised. **Remedy:** keep the fail-closed religious filter, resolve the P0 source/grade/tier review per record, populate approved metadata and add a contract test against the real release asset asserting expected nonempty eligible categories; surface a user-visible scheduling failure until then.

5. **P0 Release Blocker — credible provenance gap — khatm dua and dedication formulas.** `assets/data/khatm_dua.json:3`–`:16` declares scholar/owner approval for the long Arabic prayer and inserts, but `sourceLocator` names a broad King Fahd Mushaf appendix without an exact edition/page/URL, item text comparison, or reproducible review evidence. The app loads and displays `arabicText` from the asset (`lib/features/khatmah/data/datasources/khatm_dua_datasource.dart:91`–`:96`; `lib/features/khatmah/presentation/pages/khatm_dua_page.dart:309`) and allows copying it (`:56`–`:70`). **Status:** declared review is present; source-level agreement and specific dedication rulings are unknown. **Remedy:** preserve the owner's scholar sign-off, add the specific edition/link and per-section comparison or identify this clearly as an original general supplication; record the precise basis for each dedication template and its display wording under the source policy. Keep this as P0 pending that evidence, without claiming the prayer is substantively wrong.

6. **P0 Release Blocker — credible recitation association risk — all six selected reciters.** `lib/core/services/quran_reciter.dart:1`–`:42` supplies names and EveryAyah directories but no explicit riwayah, source edition, rights record, or audio hashes; `lib/core/services/quran_audio_service.dart:9`–`:16` builds `SSSAAA.mp3` URLs for all `(surah, ayah)` IDs. `lib/core/services/quran_continuous_player_service.dart:467`–`:470` correctly uses `numberInSurah`, and EveryAyah's index supports the general naming scheme; no complete per-reciter file existence/content/segment check is present. A wrong or missing clip would teach/mark the wrong verse or interrupt recitation. **Status:** association is plausible, not verified end-to-end and no wrong clip proven. **Remedy:** record reciter/riwayah/source/rights and verify representative beginning, middle and final ayahs for each selected reciter plus automated all-ID availability/segment mapping; prioritize boundary cases and memorization prompts. Treat unresolved Quran-audio alignment as P0 per the safety contract.

## Verified strengths and remaining unknowns

- Internal Quran structure is coherent: 114 surahs, 6,236 ordered ayahs, every numbered verse contiguous, 604 pages, 30 juz, matching `surahs.json` first-page/juz fields. The official Complex note about 27:56–59 being juz 20 agrees with the bundle. All 126 distinct daily references exist. All four manifest SHA-256 values match the current files. This does **not** constitute a full official text comparison.
- Quran ayah display in onboarding, home daily card and listening quiz is loaded from the bundled repository; no static hand-typed ayah was found in those paths (`lib/features/onboarding/presentation/widgets/onboarding_source_ayah.dart`, `lib/features/home/domain/usecases/get_ayah_of_day_usecase.dart`, `lib/features/memorization_plus/data/listening/listening_quiz_source.dart`). Audio URL creation uses per-surah verse number rather than global ordinal.
- Unknown pending device/source checks: exact glyph display for all QCF pages, full official corpus diff including orthographic variants, all reciter clip identity and timing, visual equivalence of copy/share/notification rendering, and a record-by-record scholar audit for the 116 adhkar and the khatm dua. No external data or code was changed.
