**التاريخ:** 2026-09-24

## 1. ملخص تنفيذي

المشروع يملك الآن **تصميماً معتمداً كاملاً** لميزة Talia Companion V1 و**خطة تدقيق (Phase 0) جاهزة للتنفيذ**، لكن التدقيق نفسه **لم يُنفَّذ بعد**، ولا توجد خطط تنفيذ تفصيلية، ولا أي كود للميزة.

الفجوة الحالية ليست في التصميم بل في **الانتقال من الورق إلى الكود**. الطريق الصحيح — كما يفرضه المستندان نفسهما — هو تسلسل إلزامي من مراحل كبرى، لا يجوز القفز فوق أي منها:

```text
المرحلة 0: تدقيق المستودع الفعلي (Phase 0 Audit)
        ↓ بوابة: تقرير تدقيق مكتمل بلا placeholders
المرحلة 1: كتابة خطتي تنفيذ TDD (Core + Voice Pilot)
        ↓ بوابة: خطتان file-by-file معتمدتان
المرحلة 2: تنفيذ Talia Companion Core (بدون صوت)
        ↓ بوابة: Core يعمل بالكامل و Voice Pilot مُعطَّل
المرحلة 3: تنفيذ Kids Voice Pilot فوق Core
        ↓ بوابة: قتل مستقل (kill switch) + خصوصية + QA
المرحلة 4: QA تشغيلي وأداء وإتاحة وإطلاق تدريجي
```

## 2. الوضع الحالي للمستودع (حقائق تم التحقق منها)

| البند | الحالة الفعلية |
|---|---|
| الفرع / المرجع | `main` @ `8c772d1` |
| مواصفة التصميم | ✅ موجودة ومعتمدة |
| خطة Phase 0 | ✅ مكتوبة، ❌ **لم تُنفَّذ** |
| تقرير التدقيق `docs/superpowers/audits/...` | ❌ غير موجود (مجلد `audits` غير منشأ بعد) |

| شجرة العمل | ⚠️ **تعديلات غير مُرسلة** لميزة أخرى (Prayer Delivery V2: notifications, prayer_sound, settings, ملفات android/ios أصلية) + ملفات غير متتبعة |

### ملاحظة حرجة قبل بدء أي عمل

شجرة العمل الحالية تحمل عملاً قيد التقدم لميزة **Prayer Delivery** (تعديلات على `notification_service.dart`, `prayer_sound.dart`, `lib/core/prayer_delivery/`, ملفات Android/iOS الأصلية، واختبارات). تنفيذ Phase 0 نفسه يشترط تسجيل هذه الحقيقة وعدم المساس بها، لكن الأصح إدارياً هو **فصل/إرسال هذا العمل أولاً** (أو على الأقل تثبيت baseline واضح) حتى لا تختلط نتائج `flutter analyze` / `flutter test` ولا تدخل ملفات غير متعلقة في أي commit خاص بـ Talia. هذا قرار يحتاج تأكيد المستخدم (راجع القسم 7).

## 3. قراءة تحليلية للمستندين

### 3.1 مواصفة التصميم — ماذا تفرض؟

المواصفة ليست وصفاً تسويقياً بل عقداً هندسياً. أهم الالتزامات التي ستحكم كل سطر كود قادم:

1. **المعمارية:** `Central Companion Coordinator + Feature Adapters + Local Presentation Slots` — قرار مركزي، عرض محلي تملكه كل شاشة، **ممنوع أي overlay عائم عام**.
2. **محرك أولويات P0–P10** حيث "الكبت يسبق التفاعل"، و**تركيز القرآن يفوز دائماً** (`presence = hidden` في كل أسطح القراءة).
3. **نظام شخصية حالاتي** (11 وضعاً ثابتاً + 3 تسلسلات PNG متحركة) — ممنوع تكرار صورة واحدة، وكل حالة = وضعية + سلوك حركة + بديل reduced-motion.
4. **الحضور التكيفي للبالغين:** قواعد deterministic معلنة (لا نقاط خفية)، التخفيض أسرع من الترقية، والاختيار اليدوي يتغلب على التكيف دائماً.
5. **Kids Voice Pilot (V1 فقط):** Push-to-Talk، عربي أولاً، **6 نوايا مغلقة فقط** (`start, next, repeat, back, help, finish`)، تعرّف على الجهاز أولاً مع fallback سحابي اختياري، لا TTS تشغيلي، لا تخزين صوت طفل أو نصوص كاملة، موافقة **لكل طفل ومُرقَّمة الإصدار**.
6. **حوكمة دينية صارمة:** كتالوج رسائل مغلق بمراجعات، لا توليد آيات/أحاديث/فتاوى/تفسير ديناميكياً، لا لغة ذنب.
7. **قناة احتفال واحدة في اللحظة** وإشعارات انتقائية فقط.
8. **أعلام ميزات مستقلة:** `TALIA_COMPANION_ENABLED` و `TALIA_KIDS_VOICE_PILOT_ENABLED` — الطيار الصوتي يُعطَّل دون تعطيل المرافق البصري.

### 3.2 خطة Phase 0 — ماذا ستنتج؟

خطة التدقيق مكوّنة من 6 مهام وبوابة إتمام، وهي **لا تكتب أي كود ميزة**. مخرجاتها:

| المهمة | المخرج الأساسي |
|---|---|
| Task 1 — Baseline | ترويسة تدقيق: فرع/commit، إصدارات Flutter/Dart، حالة `flutter analyze` و `flutter test`، جرد الحزم |
| Task 2 — Routing/Surfaces | خريطة دقيقة للمسارات والأسطح: من يملك Home Hero، الأهداف المضمّنة للبالغين، Kids Journey، وقائمة قاطعة بأسطح القرآن التي يجب أن تكون `hidden` |
| Task 3 — State Owners | جدول "مالكي الحالة الموثوقين" (صوت قرآن، تسجيل، ملفات أطفال، مراجعة مستحقة، استئناف، صلاة، سؤال يومي، SmartCoach) + الحد الأدنى من الـ Adapters المبرَّرة |
| Task 4 — Assets/Motion/L10n/Governance | مسار الأصول المتوافق مع `pubspec.yaml`، اصطلاحات reduced-motion الحالية، التوكنز التصميمية، ملفات ARB وأمر التوليد، اختبارات الحوكمة الدينية |
| Task 5 — Infrastructure | قرارات إعادة استخدام: إشعارات، تحليلات، أعلام، أذونات مايك، تعرّف صوتي، تخزين موافقة لكل طفل + قائمة القرارات التي تتطلب موافقة المستخدم |
| Task 6 — Implementation Map | جدولا دمج دقيقان (Core + Voice Pilot) بمسارات ورموز حقيقية، refactors مستهدفة فقط، وقرارات/عوائق صريحة |

### 3.3 العلاقة بين المستندين

التصميم هو **مصدر الحقيقة للسلوك المنتج**؛ التدقيق هو **مصدر الحقيقة لمسارات الكود**. المواصفة نفسها تمنع معاملة التدقيقات القديمة كمرجع (Section 3)، وتمنع القفز من التصميم إلى التنفيذ مباشرة (Section 29). لذلك أي محاولة لكتابة كود قبل اكتمال Phase 0 تعد مخالفة للمواصفة ذاتها.

## 4. خطة التنفيذ المنظمة (تفصيل المراحل)

### المرحلة 0 — تدقيق المستودع (إلزامية، بدون كود)

**المدخل:** خطة Phase 0 الحالية + المواصفة.
**آلية التنفيذ:** حسب الخطة: `superpowers:subagent-driven-development` (مُوصى به) أو `superpowers:executing-plans`، مهمة-بمهمة مع checkboxes.

**خطوات التنفيذ العملية:**

1. **تثبيت الـ baseline:** التقاط الفرع/commit، إصدارات Flutter/Dart، نتيجة `flutter analyze` و `flutter test` كما هي (تسجيل الأعطال الموجودة مسبقاً دون إصلاحها).
2. **إنشاء التقرير:** `docs/superpowers/audits/2026-09-19-talia-companion-v1-phase0-audit.md` بالترويسة المحددة حرفياً في Task 1 / Step 6.
3. **تنفيذ المهام 2–5 بالبحث المنهجي** (`rg`, `find`) وتوثيق الحقائق فقط: مسارات فعلية، رموز فعلية، و"absent" صريحة لأي نظام غير موجود (مثل SmartCoach إن لم يوجد).
4. **المهمة 6:** بناء جدولي الدمج. القاعدة الذهبية: *كل صف إما مسار/رمز حقيقي أو يُحذف مع سبب مكتوب — لا أسماء تخمينية*.
5. **فحص البوابة:** لا `TBD/TODO/<placeholder>`، وكل بند من البنود الـ 21 غير القابلة للتفاوض (Task 6 / Step 6) له مالك تنفيذ أو اختبار.

**مخاطر متوقعة في هذه المرحلة ومعالجتها:**

- التعديلات غير المرسلة الحالية قد تلوث الـ baseline → توثيقها وعدم لمسها.
- غياب أنظمة يفترضها التصميم (SmartCoach، Quran Learning Journey، مزود تعرّف سحابي) → تُسجَّل `absent` وتتحول لقرارات/عوائق، لا تُخترع تحت Talia.

**بوابة الإتمام:** كل شروط "Phase 0 Completion Gate" متحققة + commit مستقل للتوثيق فقط.

### المرحلة 1 — كتابة خطتي التنفيذ (بدون كود)

بعد اكتمال التدقيق، يُستخدم `superpowers:writing-plans` لإنتاج:

1. **`docs/superpowers/plans/2026-09-19-talia-companion-v1-core.md`**
   يجب أن ينتج مرافقاً بصرياً/سياقياً **كاملاً** مع Voice Pilot مُعطَّل تماماً. يغطي: النماذج الدلالية (`TaliaCompanionState`, Surface, Presence, VisualState, InteractionMode)، Context Snapshot، الـ Coordinator، سياسات الكبت والأولوية، الحضور التكيفي، الثبات (persistence)، مُصيِّر الشخصية + PNG sequences، Home Hero، Compact Assist Strip، Kids Journey Guide، كتالوج الرسائل، تنسيق الاحتفالات، الإشعارات، علم الميزة، الحوكمة، واختبارات الأداء.

2. **`docs/superpowers/plans/2026-09-19-talia-kids-voice-pilot-v1.md`**
   طبقة فوق Core العامل، قابلة للقتل المستقل. تغطي: نموذج الموافقة المُرقَّم لكل طفل، مستودع الموافقة، متحكم Push-to-Talk، محوّل التعرّف على الجهاز، محوّل الـ fallback السحابي (إن وُجد مزود معتمد)، مُصنِّف النوايا العربي المغلق، حارس النتائج المتقادمة (`requestId` + `childProfileId` + surface)، كتالوج الردود المسجلة مسبقاً، التحكّم الصوتي، إعادة المحاولة/البديل المرئي، القياس الآمن، علم الميزة، تدفق الإذن، سلوك عدم الاتصال.

**بوابة الإتمام:** الخطتان file-by-file بأسلوب TDD، كل مسار مستمد من التدقيق (لا من التخمين)، والصف `BLOCKED` الوحيد المسموح به هو fallback التعرّف السحابي إذا لم يُحسم المزود.

### المرحلة 2 — تنفيذ Talia Companion Core

**الترتيب الداخلي المقترح** (مشتق من Section 29 بالمواصفة، ويُضبَّط نهائياً وفق نتائج التدقيق):

| التسلسل | الحزمة | معيار القبول الأساسي |
|---|---|---|
| 1 | النماذج الدلالية + سياسات الكبت/الأولوية | اختبارات وحدة: أسبقية الكبت، فوز تركيز القرآن دائماً |
| 2 | Context Snapshot + الحد الأدنى من الـ Adapters | لا منطق عمل مكرر — قراءة فقط من الملاك الحاليين |
| 3 | مُصيِّر الشخصية + micro-motion + PNG sequences + reduced-motion | كل حالة لها وضعية وحركة وبديل؛ توقف كامل عند offstage/background |
| 4 | Adult Home Hero | رسالة واحدة + CTA واحد فقط (widget test) |
| 5 | Adult Compact Assist Strip | مضغوط، يظهر فقط عند الجدوى، ليس Hero ثانياً |
| 6 | Kids Journey Guide | حضور `guide` في الخريطة/البداية/التعليمات، و`hidden` في قارئ القرآن |
| 7 | الثبات + الحضور التكيفي | ترقية deterministic، تخفيض أسرع، اليدوي يغلب، عزل الأطفال |
| 8 | كتالوج الرسائل + الحوكمة + cooldowns + التدوير | رسائل مغلقة مُراجعة، اجتياز اختبارات الحوكمة القائمة/الممتدة |
| 9 | الإشعارات الانتقائية | التنقل عبر المسار الطبيعي، وإعادة حساب السياق عند الفتح |
| 10 | علم `TALIA_COMPANION_ENABLED` | تعطيل كامل نظيف للميزة |

**قواعد حاكمة أثناء التنفيذ:**

- TDD: اختبارات الوحدة للسياسات النقية أولاً، ثم widget tests للأسطح، ثم تشغيل حقيقي.
- لا commit يخلط Talia مع تعديلات Prayer Delivery الحالية.
- كل ظهور احتفالي يمر عبر سياسة "قناة واحدة".


### المرحلة 3 — تنفيذ Kids Voice Pilot

**يعتمد على:** Core العامل + حسم قرار المزود السحابي (إن طُلب الـ fallback).

**الترتيب الداخلي المقترح:**

| التسلسل | الحزمة | معيار القبول الأساسي |
|---|---|---|
| 1 | نموذج الموافقة المُرقَّم لكل طفل + المستودع | عزل كامل بين الأطفال؛ موافقة الطفل A لا تفعل B |
| 2 | تدفق الإذن Just-in-Time | لا طلب مايك أثناء الـ onboarding العام |
| 3 | محوّل التعرّف على الجهاز + متحكم Push-to-Talk | لا wake word، لا استماع دائم |
| 4 | مُصنِّف النوايا العربي المغلق (6 نوايا) | الغموض = `unknown`، ممنوع التخمين |
| 5 | حارس النتائج المتقادمة + إلغاء async | لا تنفيذ `next/back` على شاشة تغيرت |
| 6 | إعادة المحاولة ×2 ثم البديل المرئي | الفشل التقني ≠ فشل الطفل (رسائل محايدة) |
| 7 | كتالوج الردود الصوتية المسجلة | ملفات ثابتة مُراجعة، لا TTS |
| 8 | التحكّم الصوتي (أولوية: قرآن/تسجيل > إدخال صوتي > رد Talia) | كبت فوري عند صوت قرآن أو تسجيل |
| 9 | القياس الآمن | الأحداث المسموحة فقط؛ ممنوع rawAudio/transcript/اسم الطفل |
| 10 | علم `TALIA_KIDS_VOICE_PILOT_ENABLED` + سلوك عدم الاتصال | تعطيل مستقل؛ استمرار جزئي offline |
| 11 | (اختياري/محظور حتى الحسم) fallback سحابي | **BLOCKED** حتى اختيار مزود والتحقق من خصوصيته |

### المرحلة 4 — QA تشغيلي، أداء، إتاحة، وإطلاق تدريجي

لا يُقبل الأداء بفحص الكود (Section 27). الاختبارات التشغيلية الإلزامية على أجهزة/محاكيات Android مستهدفة:

- انتقالات المسارات وسلوك IndexedStack/Offstage (لا حلقات إطارات خفية).
- كبت الصوت والتسجيل، إلغاء الصوت عند التنقل، تبديل الملفات، الخلفية/الاستئناف.
- سيناريوهات إذن المايك (رفض/قبول)، عدم الاتصال، الثقة المنخفضة، مسار الـ fallback.
- قياس jank أثناء الحركات، نمو الذاكرة عند تغيّر الحالات، فك ترميز الصور، أداء تمرير Home Hero، وفئات زمن الاستجابة الصوتية.
- التحقق من قتل الميزتين عبر العلمين بشكل مستقل.

## 6. المخاطر الرئيسية ومعالجتها

| الخطر | الأثر | المعالجة |
|---|---|---|
| القفز للتنفيذ قبل اكتمال Phase 0 | مسارات/رموز تخمينية، ازدواجية منطق، هدر | التسلسل الإلزامي في هذا التقرير + بوابة التدقيق |
| خلط عمل Prayer Delivery غير المرسل مع Talia | commits ملوثة، baseline مضلل | فصل/إرسال العمل الحالي أولاً أو توثيقه صراحة (قرار مستخدم — القسم 7) |
| غياب مزود تعرّف سحابي معتمد | تعطّل صف الـ fallback | يبقى `BLOCKED` صراحة؛ بقية Voice Pilot يتقدم على الجهاز فقط |
| غياب أنظمة يفترضها التصميم (SmartCoach/رحلة تعلم) | مرشحون أقل لـ Home Hero | تُسجَّل `absent` في التدقيق؛ Talia يحكم بين الموجود فقط ولا يبني بدائل |
| أصول الشخصية/الصوت غير جاهزة (11 وضعية + 3 تسلسلات + ردود صوتية عربية) | تعطّل المرئيات والردود | قرار إنتاج أصول خارج الكود يُدرج في "القرارات المطلوبة" قبل المرحلتين 2–3 |
| ضغط الأداء من تسلسلات PNG | jank/ذاكرة | قيود الأداء في §12 + قياس فعلي في المرحلة 4 |
| تسرب حالة بين ملفات الأطفال | خرق خصوصية | حارس `requestId/childProfileId` + اختبارات التبديل والعزل |

## 7. قرارات مطلوبة من المستخدم قبل/أثناء التنفيذ

1. **مصير التعديلات غير المرسلة الحالية** (Prayer Delivery): إرسالها/فصلها في فرع قبل بدء Phase 0، أم توثيقها كـ baseline مشوش مقبول؟ *(موصى به: الفصل أولاً)*
2. **مزود التعرّف الصوتي السحابي** (إن رُغب بالـ fallback): اختيار المزود + التحقق الفعلي من سياسة الاحتفاظ/الخصوصية قبل أي ادعاء — لا تخمين.
3. **إنتاج أصول الشخصية**: من ينتج/يعتمد الـ 11 وضعية و3 تسلسلات (wave/listening/celebrate) مع ضبط هوية الشخصية (§11 Asset consistency)؟
4. **إنتاج الردود الصوتية**: صوت Talia المعتمد الواحد، وتوليد/تسجيل كتالوج `voice.*` العربي مسبقاً.
5. **سياسة الالتزامات (commits)**: هل يُسمح بإرسال وثائق التدقيق المرحلية (Task 1/Step 7 يطرح هذا الخيار)؟
6. **عتبات الحضور التكيفي النهائية**: المواصفة تسمح بضبطها أثناء التنفيذ واختبار القابلية — تحتاج تأكيداً عند كتابة خطة Core.

## 8. التوصيات التنفيذية الفورية (بالترتيب)

1. حسم قرار (1) أعلاه بشأن شجرة العمل الحالية.
2. تنفيذ خطة Phase 0 كما هي، مهمة-بمهمة، باستخدام `superpowers:subagent-driven-development`، وإنتاج `docs/superpowers/audits/2026-09-19-talia-companion-v1-phase0-audit.md` خالٍ من أي placeholder.
3. عند اجتياز بوابة Phase 0: توليد الخطتين في `docs/superpowers/plans/` عبر `superpowers:writing-plans`.
4. تنفيذ Core أولاً حتى يعمل كاملاً والصوت مُعطَّل، ثم Voice Pilot كطبقة مستقلة القتل.
5. عدم إعلان النجاح إلا بعد اجتياز معايير §28 الخمسة عشر وقياسات الأداء الفعلية في المرحلة 4.
