# Talia Quran – Master Technical Product Guide

## 1. Architectural Overview (Clean Architecture)
Talia is structured using a strict **Feature-First Clean Architecture**. The application is deeply modular and completely decoupled to ensure high testability, scalability, and maintainability.

### 1.1 Core Layers
1. **Presentation Layer:** Contains UI Widgets, Pages, and **Cubits** (from `flutter_bloc`) for State Management. Riverpod or other state management solutions are strictly prohibited.
2. **Domain Layer:** Contains pure business logic. Encompasses Entities, Repositories Interfaces, and UseCases. *(Zero Flutter imports allowed here).*
3. **Data Layer:** Contains Repository Implementations, Local DB logic (`Isar`), Remote DB (`Supabase`), and Data Sources.

### 1.2 Tech Stack
- **Framework:** Flutter (>=3.22), Dart (>=3.4)
- **State Management:** `flutter_bloc` (Cubits specifically)
- **Routing:** `go_router`
- **Dependency Injection:** `get_it` (Strictly manual registration in `injection.dart`, no annotations/build_runner for DI)
- **Local Database:** `isar` (NoSQL) + `shared_preferences`
- **Backend:** `supabase_flutter` (Auth, Database syncing, Storage)
- **Audio & STT:** `just_audio` (Playback), `speech_to_text` (Recitation Analysis)
- **UI & Animations:** `qcf_quran_plus` (Quran Font rendering), `flutter_animate` (Micro-animations)

## 2. Directory Structure (Feature-First)
To maintain the Clean Architecture, the project must follow this exact structure:
```text
lib/
├── core/                        # Shared Utilities, Network, DI (GetIt), Routing, Theme
└── features/                    # Independent Feature Modules
    ├── auth/                    # Supabase Session, Guest Mode, Registration

    ├── kids_journey/            # Kids Gamified UI
    ├── parent_dashboard/        # Guardian Linking, Remote Tracking

```

## 3. Database Schema & Data Strategy

### 3.1 Local vs Remote (Offline-First)
Talia is strictly an **Offline-First** application.
- **Local Truth (`Isar`):** All fast reads, session tracking, and offline progress must be written immediately to Isar.
- **Remote Sync (`Supabase`):** A background sync service reads un-synced Isar records and pushes them to Supabase, pulling down updates from the server using a `last_synced_at` timestamp strategy.

### 3.2 Key Entities & Models
1. **User / Profile:** Supabase Auth User ID + Profile data (Name, Avatar, IsChild flag, GuardianId).
2. **AyahReviewRecord:** Tracks every recitation attempt. Fields: `ayahId`, `strengthLevel`, `nextReviewDate`, `intervalDays`, `createdByMode` (Adult vs Kids).
3. **SessionRecord:** Tracks incomplete sessions for resume capability.
4. **GamificationRecord:** Tracks `XP`, `CurrentStreak`, `LongestStreak`, and `UnlockedBadges`.

---

## 4. Memorization Engine (The Core Logic)

The Memorization Engine is a **Pure Domain Stateless Class** (`SessionEngine`) located at `lib/core/memorization/v2/session_engine.dart`. It drives the application logic completely independent of the UI.

### 4.1 State Machine (Session Phases)
The `SessionState` flows synchronously:
1. `created` → 2. `learning` → 3. `memorizing` → 4. `reciting` → 5. `remediation` (if failed) → 6. `blockReviewPending` → 7. `blockReview` → 8. `completed`.

### 4.2 STT Recitation Evaluator
Handled by `recitation_evaluator.dart`:
- **Normalization:** Relies on `ArabicNormalizer` to strip harakat, tatweel, spaces, and hamza variations before comparing.
- **Threshold:** The Jaccard token-overlap similarity must be `>= 0.92`.
- **No-Attempt Guard:** Empty STT callbacks do not count as failures, merely `noAttempt`.

---

## 5. Security & Authentication Strategy (Supabase)

1. **Guest Mode:** Permitted only for reading the Quran (Quran Feature).
2. **Protected Routes:** `go_router` must use a redirect guard to push users to Auth if they try to access Memorization, Dashboards, or Settings.
3. **Guardian Linking (Parent-Child):**
   - Implemented via a unique short code or QR Code generated by Supabase.
   - Row Level Security (RLS) policies in Postgres ensure a parent can only fetch records where `guardian_id = my_uid`.

## 6. Development Guidelines & Strict AI Rules

Any AI Agent or Developer working on Talia **MUST** adhere to the following rules:

1. **NO UI Dependencies in Domain Layer:** Domain folders must never import `package:flutter` or use `BuildContext`.
2. **Backward Compatibility is Non-Negotiable:** Any feature toggled must gracefully fallback to legacy flows if disabled.
3. **No Text Rendering in Testing Phases:** Recitation and Block Review pages must rely on hidden cards. Rendering `QuranText`, `qcf_quran`, or `ayahText` widgets in these phases is a critical violation of product specs.
4. **Cubit Lifecycle Enforcement:** Ensure proper resource cleanup in Cubit's `close()` method:
   - Cancel `SpeechToText` (`speech.stop()`, `speech.cancel()`).
   - Stop and dispose `just_audio` player instances.
   - Cancel all `StreamSubscriptions`.
5. **State Transitions:** Do not mutate `SessionState` manually inside the Cubit. Always route transitions through the pure `SessionEngine` methods.
6. **Certificate Policy:** All review sources (`Hifz`, `KidsMode`, `SessionRecords`, `Migration`) must count towards the completion certificates logic within `AchievementService`.
